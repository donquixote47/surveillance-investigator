# 00 - Scope

## One sentence

An AI agent on Amazon Bedrock AgentCore that investigates spoofing and layering alerts raised by a trade-surveillance detector, assembles the evidence a Level-1 analyst would assemble, writes an auditable investigation report, and proposes a disposition that a human then records.

## Why this and not the sanctions idea

The project started as a sanctions-screening alert investigator for cross-border payments. We kept the shape of the idea and changed the domain. Reasons, in order of weight:

1. **It is George's customers' problem.** His AWS customers are brokers, trading firms and some HFT firms. Every one of them has a market-abuse surveillance obligation (EU MAR Art. 16(2); MiFID II Art. 17 / RTS 6 for algorithmic traders; FINRA 3110 in the US). Few of them run large payment flows, so sanctions screening is a small part of their compliance work. See `01-domain-primer.md`.
2. **Same pattern, so nothing learned is lost.** Deterministic detector produces alerts; most are false positives; a human investigates each one; the regulator wants the reasoning written down. The architecture on AgentCore is identical. Only the tools and the data change.
3. **Synthetic data is more credible here.** Spoofing lives entirely in order and trade events, which a simulator can generate with ground truth. Sanctions investigation leans on identity data (dates of birth, addresses, registries) that is hard to fake convincingly.
4. **The agent has more to reason about.** Deciding whether a cancel pattern is market making, algorithmic re-pricing, a risk-limit cut, or manipulation requires multi-step evidence gathering and a written argument. That is what a general-purpose agent adds over a classifier.
5. **Competitive position is similar, so no loss there.** Both markets have incumbents (sanctions: Silent Eight, WorkFusion; surveillance: NICE Actimize, Nasdaq, Eventus). In both, agentic investigation of alerts is the newer layer and small and mid-sized firms are underserved.

The sanctions version is archived at `shared/tam-work/archive/agentcore-sanctions-triage-2026-09/` for reference. It is mentioned in the presentation in one line as a second plug-in for the same core.

## In scope

| Dimension | Decision |
|---|---|
| Abuse type | Spoofing and layering only. One detector, one scenario family, investigated deeply. |
| Asset class | Cash equities. |
| Venue | One lit order book (a single simulated exchange). No cross-venue, no cross-asset. |
| Participants | A firm's own traders and algos plus its clients' order flow, as a broker would see it. |
| Input | One alert at a time from a deterministic detector we write ourselves, with the raw order and trade events around it. |
| Agent role | Level-1 analyst: gather evidence, compute discriminators, write the investigation report, propose one of three dispositions (close as false positive, escalate to Level 2, draft a STOR). |
| Human role | Records the disposition. Can override, annotate, and send feedback that the agent remembers. |
| Data | Synthetic only, generated by our own limit-order-book simulator with injected scenarios and ground-truth labels. |
| Evaluation | Labelled dataset; primary metric is the share of false-positive alerts the agent proposes to close, measured only at 100% recall on true abuse. |
| AgentCore | Runtime, Gateway (Lambda tools as MCP), Identity (Cognito, L1 and L2 groups), Policy (deterministic guardrails including temporal rules), Memory (analyst decisions and feedback), Code Interpreter (ad-hoc analysis and charts for the report), Observability (audit trail), Evaluations (ground-truth and custom evaluators), Optimization (prompt recommendations, configuration bundles, A/B through the Gateway, promoted only through the deterministic gate). |
| Deliverable | Working demo, bilingual documentation, mentor presentation with demo script. |

## Out of scope

- Real-time detection. The detector runs on completed windows; the agent works a queue.
- Building a competitive detection engine. Our detector is deliberately simple and noisy, to mimic the alert quality firms complain about.
- Other abuse types (wash trades, insider dealing, marking the close, front running, momentum ignition, quote stuffing). Mentioned in the primer so George knows the landscape; not implemented.
- Communications surveillance (chat, voice, email).
- Autonomous disposition. The agent cannot call the tool that records a disposition; AgentCore Policy forbids it at the Gateway. This is a design principle, not a phase-1 limitation.
- Multi-asset or cross-venue analysis.
- Production hardening (multi-region, DR, SLAs), customer data, or anything from George's actual customers.
- Filing a STOR with a regulator. The agent drafts the narrative fields of a STOR; nothing is submitted anywhere.

## Stretch items (only if the core is finished and evaluated)

- Replace or supplement our simulator with ABIDES (J.P. Morgan's open-source agent-based market simulator) for more realistic background flow.
- A Level-2 reviewer agent that receives escalations over A2A and challenges the L1 report.
- Online evaluation on live traffic and a second Optimization iteration.
- A thin sanctions plug-in reusing the same core, to show the architecture generalises.

## Success criteria for the TFC presentation

1. A mentor who has never seen trade surveillance understands the problem in five minutes from the docs and the demo.
2. The demo shows one true spoofing case and two or three false-positive scenarios investigated end to end, with the report, the proposed disposition and the evidence.
3. The demo shows the Gateway denying the agent an action (recording a disposition, or proposing a close before gathering evidence) and the denial visible in the policy logs.
4. The evaluation table shows the metric on the full labelled dataset, with the number of true cases missed at zero.
5. Every AgentCore service in the "in scope" row is exercised for a reason George can explain in two sentences.
