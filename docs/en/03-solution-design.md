# 03 - Solution design

## 1. Architecture

```
                     ┌──────────────────────────────────────────────────────────────┐
                     │                      "The firm" (mock back end, CDK)          │
                     │  DynamoDB: alerts, order_events, trades, traders, events,     │
                     │            cases, dispositions                                │
                     │  S3: synthetic market data (parquet), reports                 │
                     │  Lambda: one function per tool (src/tools/)                   │
                     │  Cognito: user pool, groups L1 and L2                         │
                     └───────────────▲──────────────────────────────▲───────────────┘
                                     │ invoke (Gateway IAM role)    │ invoke (direct, human path)
                     ┌───────────────┴───────────────┐    ┌─────────┴────────────────────┐
                     │  AgentCore Gateway            │    │  Analyst UI (Streamlit/CLI)  │
                     │  target "surv" -> MCP tools   │    │  Cognito login as L1 or L2   │
                     │  inbound: Cognito JWT         │    │  reads report, records       │
                     │  Policy Engine (ENFORCE)      │    │  disposition, sends feedback │
                     │  per-user rate limits         │    └─────────┬────────────────────┘
                     └───────────────▲───────────────┘              │ invoke agent
                                     │ MCP                          │
                     ┌───────────────┴──────────────────────────────▼───────────────┐
                     │  AgentCore Runtime: Strands agent "L1 investigator"          │
                     │  - reads alert, calls tools in evidence order                │
                     │  - Code Interpreter for ad-hoc analysis and charts           │
                     │  - Memory: trader/instrument namespaces, analyst feedback    │
                     │  - writes InvestigationReport (JSON) -> propose_disposition  │
                     └───────────────┬──────────────────────────────────────────────┘
                                     │ OTel traces + policy decision logs
                     ┌───────────────▼───────────────┐    ┌──────────────────────────────┐
                     │  AgentCore Observability      │───▶│  AgentCore Evaluations        │
                     │  (CloudWatch)                 │    │  ground truth + custom        │
                     └───────────────────────────────┘    │  evaluators; our harness      │
                                                          │  computes the gate + metric   │
                                                          └──────────────────────────────┘
```

Two paths touch the back end. The agent path goes through the Gateway, where Policy decides on every call. The human path goes from the analyst UI to a small set of Lambdas (record disposition, send feedback) with the analyst's Cognito identity, and never through the agent. The tool `record_disposition` is deliberately not registered as a Gateway target tool at all, so the agent cannot discover it, and a Policy rule forbids it anyway in case someone adds it later. Belt and braces.

## 2. AgentCore services and why each one

| Service | Role here | Why this primitive |
|---|---|---|
| **Runtime** | Hosts the Strands agent as an HTTP agent; one session per alert investigation. | Isolated microVM per session gives per-alert isolation; versions and endpoints let us pin a `demo` endpoint. |
| **Gateway** | Turns the tool Lambdas into MCP tools under target `surv`; enforces inbound JWT; applies per-user rate limits; attaches the Policy Engine. | Single choke point for every agent action. Without it, Policy has nothing to intercept. |
| **Identity** | Cognito user pool as inbound JWT provider; groups `L1`, `L2`; agent workload identity. | Lets policies and rate limits key on *who* is driving the agent, and lets the human path carry a different identity from the agent path. |
| **Policy** | Deny-by-default Cedar/Dogwood rules: which tools, in what order, how many times, never `record_disposition`. | Deterministic control outside the prompt. The temporal rules (evidence before conclusion) are the demo's strongest moment. |
| **Memory** | Episodic and semantic records per trader and instrument: past dispositions, analyst corrections, firm procedures text. | The agent should know "this trader is a registered market maker and the last six alerts were closed for that reason" without being told each time, and should learn from overrides. |
| **Code Interpreter** | Ad-hoc computation and charts for the report (price path with order placements and cancels overlaid). | Keeps arbitrary code off the Runtime and out of the Lambdas; the deterministic metrics stay in Lambda for reproducibility. |
| **Observability** | OTel traces of every step; policy decision logs. | This *is* the record-keeping requirement. |
| **Evaluations** | Ground-truth evaluators (expected disposition, assertions, tool trajectory) and a custom evaluator for rationale quality; on-demand runs over the labelled dataset. | Regression gate before any prompt or tool change. |
| **Optimization** | Recommendations for the system prompt and tool descriptions generated from traces against our rationale evaluator; versioned configuration bundles; A/B test of a candidate bundle through the Gateway; promotion only if the deterministic gate holds. | The governed answer to "does it get better?": measured, versioned, human-approved changes, never silent drift. See section 11. |
| Registry, A2A (stretch) | Publish the agent; L2 reviewer agent. | Only if the core is done. |

## 3. Data model (synthetic)

All ids are synthetic. Timestamps are integer nanoseconds since the epoch in the simulator and in parquet; the loader keeps them as integers in DynamoDB (so range queries on the sort key work) and every tool adds a `time` field (`HH:MM:SS.mmm`) next to each `ts` for the agent and the reader. Prices are integer ticks (`price_ticks`, tick size in `instrument_stats`). Every table carries a `date` column (one simulated session day).

**DynamoDB keys** (`src/tools/ddb_items.py` builds them, `src/tools/data_access.py` queries by them; table names are `surv-<name>` with underscores as hyphens): `order_events` pk `<trader_id>#<date>`, sk `<ts:019d>#<seq:06d>` with a GSI `by_date` (`date`, `sk`) so one query returns a trader's day and another the whole market around a timestamp; `trades` and `market_events` pk `date`, sk `<ts:019d>#<id or type>`; `traders` pk `trader_id`; `instrument_stats` pk `instrument`, sk `date`; `alerts` pk `alert_id` plus an attribute `trigger_sk` = `<trigger_ts:019d>#<alert_id>` for the GSI `by_date` that feeds the analyst's queue; `cases_history` pk `trader_id`, sk `<date>#<alert_id>`; `cases` pk `alert_id` with a GSI `by_trader` (`trader_id`, `proposed_at`). `seq` is the event's position within its day after a stable sort by `ts`, so two events in the same nanosecond keep the simulator's order. Zero-padding `ts` to 19 digits makes string comparison equal numeric comparison. NaN and None attributes are dropped at load time.

## 4. Tool contracts (Gateway target `surv`)

All twelve tools live in **one** Lambda (`surv-gateway-tools`, `src/tools/lambda_handlers/gateway_tools.py`), each with an input and output JSON schema declared on the Gateway target (`src/tools/schema.py`, exported to the target's inline `toolSchema`). The Gateway invokes the Lambda with the tool's input properties as the event and the full tool name (`surv___get_alert`) in `context.client_context.custom['bedrockAgentCoreToolName']`; the handler strips the target prefix and dispatches. One function rather than twelve because a Gateway target maps one Lambda ARN to one tool schema and the target name is the policy prefix; least privilege is then applied at the data layer (the function may read every table and write only `surv-cases`, and it has no code path that sets a recorded disposition). Missing required inputs and unknown tools return `{"error": ...}` so the agent sees why, instead of a Lambda exception; an exception inside a tool is caught and returned the same way. The six evidence tools answer with `alert_id` only when they answered for that alert, and an error answer never carries it (2026-11-17): that field is what policies 03a, 03b and 04 match (section 6). Output fields that policies reference are marked. Tool names are what the agent sees after the Gateway prefix: `surv___get_alert` etc.

## 5. InvestigationReport schema

The agent must produce this structure. The strict version is the pydantic model `InvestigationReport` in `app/surv_investigator_l1/report.py`; the agent's `InvestigationGuard` hook validates the report against it **before** `propose_disposition` leaves the agent (a Strands `BeforeToolCallEvent` with `cancel_tool`), and hands the validation errors back to the model as the tool result, so a malformed or inconsistent report never reaches the Gateway. The model's rules beyond shape: `evidence[].source` must be one of the tools (or `memory`); a `ruled_out` explanation must cite evidence ids that exist; a CLOSE_FP needs at least one explanation with verdict `supported`; an ESCALATE or DRAFT_STOR must carry none. `tool_calls` is not written by the model: the guard fills it from the calls it observed, so the trajectory in the report is the real one. The guard also refuses a second proposal in the same run, a proposal for another alert id, and `draft_stor_narrative` outside `stor_drafting` mode (which `main.py` grants only to tokens whose `cognito:groups` contains L2). One tolerance, added 2026-11-10 after measurement: the model wrote `ruled_out` for `ruled_out_by` in 14% of sessions (sometimes alone, sometimes beside an empty `ruled_out_by`), and each rejection cost a full report rewrite; the `Explanation` model now folds that one name into the declared field before validation and emits only `ruled_out_by`, while every other unknown key is still refused.

```json
{
  "alert_id": "A-000123",
  "scenario": "SPOOFING",
  "summary": "One paragraph an L2 can read in 30 seconds.",
  "evidence": [
    {"id": "E1", "source": "compute_discriminators", "fact": "OTR 48:1 in window vs trader typical 6:1"},
    {"id": "E2", "source": "get_trader_profile", "fact": "Trader is not a registered market maker on XYZ"},
    {"id": "E3", "source": "get_market_events", "fact": "No public events within ±60s"}
  ],
  "indicators_matched": ["orders with no intention to execute", "opposite-side fill before cancel"],
  "indicators_not_matched": ["two-sided symmetric cancels"],
  "legitimate_explanations_considered": [
    {"explanation": "market making", "ruled_out_by": ["E2"]},
    {"explanation": "news reaction", "ruled_out_by": ["E3"]}
  ],
  "proposed_disposition": "ESCALATE",
  "confidence": 0.78,
  "what_would_change_my_mind": "Evidence that the sell orders were child orders of a hedging parent.",
  "memory_used": ["prior disposition 2026-10-14 on same trader: CLOSE_FP, reason: pegged algo"],
  "tool_calls": ["get_alert", "get_order_events", "compute_discriminators", "get_trader_profile", "get_market_events"]
}
```

Rules the evaluator checks: every `fact` must be traceable to a tool output in the trace (evidence faithfulness); `legitimate_explanations_considered` must list every scenario row from the primer's table 2.3 that applies to the detector scenario; `proposed_disposition` must be consistent with the evidence (a CLOSE_FP with an unmatched legitimate explanation is a rubric failure).

## 6. Policy set
Policies live in `policies/` (one rule per file, `.cedar` for stateless Cedar, `.dw` for Dogwood temporal rules) and are declared in `agentcore/agentcore.json` under the Policy Engine `investigator_pe`, which `agentcore deploy` creates and attaches to the Gateway. Deny by default: every tool needs a `permit`, and a `permit` is also what makes a tool's completion count as a `::response` event for the temporal rules. Deployed and enforced since 2026-11-04 (engine mode `ENFORCE`; see the decision log for why `LOG_ONLY` could not be used to test these rules).

| # | Control | Rule type | File |
|---|---|---|---|
| 01 | Any authenticated analyst (`AgentCore::OAuthUser`) may call the ten read tools. | plain `permit`, `action in [...]` | `01-permit-read-tools.cedar` |
| 02 | Any action outside the twelve known tools is forbidden for everyone. A `record_disposition` tool cannot be named in a policy (the Cedar schema is generated from the Gateway's manifest, so an undeclared action is rejected at creation); the closed list is the strongest form the engine accepts, and a tool added later is denied until this list is edited. | `forbid ... unless action in [...]` | `02-forbid-unknown-tools.cedar` |
| 03a | `propose_disposition` is permitted only after `get_alert`, `get_order_events` and `compute_discriminators` have **returned for the same alert** in this session (`output.alert_id: context.input.alert_id`: the id in the tool's answer equals the id in the proposal). Until 2026-11-17 the match was on the call's input, which a lookup that failed also satisfied. | temporal `permit`, three `formerly within 2h ...::response` predicates (the per-policy maximum) | `03a-evidence-before-proposal.dw` |
| 03b | ... and `get_trader_profile` and `get_market_events` have returned for the same alert (the same match; until 2026-11-17 the market events were not tied to the alert). A `forbid ... unless temporal` cannot be overridden by any permit. | temporal `forbid-unless` | `03b-profile-and-market-before-proposal.dw` |
| 04 | A `CLOSE_FP` proposal additionally needs `get_trader_alert_history` to have returned for the same alert (the same match; until 2026-11-17 any completed history call in the session counted). | `forbid ... when { context.input.disposition == "CLOSE_FP" } unless temporal {...}` | `04-history-before-close.dw` |
| 05 | `draft_stor_narrative` is permitted only after a `propose_disposition` response for the same `alert_id` with `input.disposition: "DRAFT_STOR"`. Correlates on the proposal's input, which exists whether or not outputs are declared. | temporal `permit` | `05-stor-after-proposal.dw` |
| 06 | At most one `propose_disposition` per `alert_id` per session. Matching `::response` makes the self-reference safe: the request being authorised has no response yet. | temporal `forbid` | `06-one-proposal-per-alert.dw` |
| 07 | Only principals whose `cognito:groups` claim contains `L2` may call `draft_stor_narrative`. JWT claims arrive as string tags; the array claim is the text `["L2"]`, matched with `like "*L2*"`. | `forbid ... unless { principal.hasTag(...) && principal.getTag(...) like ... }` | `07-stor-drafting-requires-l2.cedar` |
| 08 | At most 6 `get_order_events` per session (`count` includes the current request, so the seventh is denied). | temporal `forbid` with `exists (n: Long). (count ...) == n && n > 6` | `08-cap-event-pulls.dw` |

Every temporal predicate carries `eventResource: resource` (mandatory). The agent sends `x-amzn-bedrock-agentcore-policy-session-id` on every Gateway call (one investigation = one policy session, the Runtime session id when there is one), and the Gateway's role has `bedrock-agentcore:GetWorkloadAccessToken` on its workload-identity directory, without which every call fails as soon as a session header is present. Validation: `scripts/validate_policies.py` creates each statement on the live engine with `FAIL_ON_ANY_FINDINGS` and prints the service's findings; the `forbid` rules trip the engine's "overly restrictive" heuristic (it cannot see that other permits exist) and are therefore declared with `IGNORE_ALL_FINDINGS`.

Observed decisions (`scripts/policy_demo.py`, 2026-11-04, engine `ENFORCE`): a proposal before any evidence -> `DENIED by p03b` (03a also fails; the forbid is reported first); `CLOSE_FP` without history -> `DENIED by p04`; after the history -> `ALLOWED`; a second proposal -> `DENIED by p06`; `draft_stor_narrative` as L1 -> `DENIED by p07`; an L1 token's `tools/list` shows **10** tools (the Gateway's `PartiallyAuthorizeActions` hides what 07 forbids). The Gateway's refusal names the policy: `Tool Execution Denied: ... [Policy evaluation denied due to p06_one_proposal_per_alert-...]`, and the vended log group `/aws/vendedlogs/bedrock-agentcore/<gateway id>` records every evaluation (`decision`, `determiningPolicies`, `clientSuppliedPolicySessionId`, `temporal_latency_ms`, about 30-60 ms). What "returned for the alert" means (2026-11-17): a `::response` event is recorded when the tool returns, and a Lambda that returns `{"error": ...}` has returned; on 2026-11-16 a profile lookup for a trader that does not exist satisfied 03b. The rules therefore match a field of the answer. The handler removes `alert_id` from any error answer of the six evidence tools, a call without `alert_id` gets none back, and the profile and history tools refuse a trader that is not the alert's own. `output.<field>` can be matched only when the target declares the field in its output schema [verified 2026-11-17, devguide "Authoring temporal policies" and "Temporal policy examples"], so the schema was deployed first and the policies in a second deploy. Observed on the live Gateway the same day (`scripts/policy_demo.py` and six one-off probes, each in its own policy session): a proposal after a profile lookup that answered with an error -> `DENIED by p03b`; after market events asked by instrument and window, without the alert id -> `DENIED by p03b`; after a profile asked without the alert id -> `DENIED by p03b`; `CLOSE_FP` after a history asked without the alert id, or asked for another trader -> `DENIED by p04`; all six evidence calls for one alert and a `CLOSE_FP` proposal for another -> denied by p04 and p03b; after an order-events call that failed inside the tool -> denied by default (`No policy applies to the request`: 03a's permit does not hold); the full sequence -> `ALLOWED`. The agent's own guard still refuses first; it is no longer the only control that does.

Session-scoped counts can be reset by starting a new session; they shape behaviour and are not a security boundary. The hard boundary is 02 plus the tool not existing on the Gateway. Gateway per-user rate limits (section 8) add a brake on volume, with a measured burst allowance of 15-20 calls, so they do not replace the count either.
## 7. Memory scheme
One Memory resource `investigator_memory` (deployed as `surv_default_investigator_memory-38ATWRDsvk`, declared in `agentcore.json`, raw-event expiry 90 days) with one built-in SEMANTIC strategy `analyst_knowledge` whose namespace template is `/traders/{actorId}/notes/`. Access code: `src/tools/memory_access.py`.

Two ways in, by design:
- **Direct records** (`BatchCreateMemoryRecords`) for facts the firm authors itself. The human-path Lambda writes one record per recorded disposition and one per feedback note; `scripts/memory_admin.py` seeds the dataset's `cases_history` and ingests the procedures. Direct records are deterministic and visible on the next call, which a system of record needs. Each carries metadata (`kind`, `alert_id`, `trader_id`, `instrument`, `date`, `recorded`, `proposed`, `override`, `recorded_by`).
- **Extraction** from a conversational event (`CreateEvent`, actor = the trader id) for the free-text feedback, so the SEMANTIC strategy distils it asynchronously. Observed: a one-sentence feedback produced two extracted facts within a minute, one of them a general rule ("a cancel within 200 ms of an unscheduled news item on a name is classified as a news reaction"); retrieval returns both kinds, marked `source: recorded by the human path` or `extracted by the semantic strategy`.

Namespaces (segments made of `[a-zA-Z0-9-_]`, so `SYN.A` is stored under `SYN_A`):
- `/traders/{trader_id}/notes/` : dispositions, overrides, feedback on this trader (direct and extracted).
- `/desks/{desk}/notes/` : the same facts fanned out to the trader's desk. The scenario traders are one per day, so a correction only reaches tomorrow's alert through the desk; the agent's `recall_memory` queries both.
- `/instruments/{instrument}/notes/` : instrument facts, written by hand with `memory_admin.py`.
- `/procedures/` : the three procedure topics, one record each.

Retrieval is a Gateway tool, `recall_memory` (alert id, trader id, instrument, free-text query), implemented in the same Lambda as the other tools, so it passes through Policy, appears in the Gateway log, and its result is a tool result the report can cite. It returns `trader_notes`, `desk_notes`, `instrument_notes`, `procedures`, each with a relevance score. The agent calls it right after `get_procedures`, before the evidence tools (prompt), and lists what it relied on in `memory_used`, one string per record, saying what it did with it. `RetrieveMemoryRecords` rejects a trailing slash in `namespace` even though `BatchCreateMemoryRecords` accepts one; the code strips it.

**Scope and cadence of recall (decided 2026-11-05, written up 2026-11-08).** The memory is the firm's, not the analyst's: one resource per deployment, records keyed by trader, desk and instrument, each carrying `recorded_by` and the override flag. Every analyst's recorded decision is visible to every later investigation, because the regulator holds the firm to one standard and the same trader must be treated the same way whoever has the shift; the cost of that choice (one analyst's mistake reaches everyone) is met by transparency (who, when, overridden or not), by the closure standard's "context, never a reason", and by Policy 03's demand for current-window evidence. Memory never crosses deployments: a consultancy serving five firms runs five. There is no per-analyst namespace, on purpose.

Recall runs once per investigation, as its own Gateway call, rather than being cached or pre-loaded. Three reasons: the content changes between investigations (a decision recorded at 10:00 must reach the 10:05 investigation of the same desk, and the writer is a different system, so a cache would need cross-system invalidation); the question is scoped to this alert's trader, desk and instrument, so there is nothing shared to cache except the procedures, which have their own tool for the same reason (a change to the standard applies on the next investigation without a redeploy, which is how iterations 1 and 2 shipped); and a Gateway call is what makes the recall auditable (Policy decision, Gateway log line, a tool result `memory_used` can be checked against). Measured cost of memory (data doc 4.6): one tool call, +16.6k input tokens and +3.4 s per alert, about 24% of model cost, most of it the recalled content being re-read on every later model turn rather than the call itself.

*Deferred optimisation.* Folding the recall into `get_alert` server-side (or a single `get_case_context` = alert + procedures + memory) would remove one or two model turns: about 8-15% of input tokens and 2-4 s per alert, since each turn re-reads the whole context. It would cost the agent's ability to ask memory a targeted question, Policy's ability to treat recall as its own action, and the clean on/off switch the memory arm needed. Not done in the alpha, where measuring memory separately came first; recommended for a production deployment once the firm's own data shows what recall is worth there, keeping `recall_memory` as a second, optional tool for targeted follow-ups.

Observed on the demo alerts (2026-11-05): B (`A-261005-0003`, market maker) cites the desk's two prior closures and says "same explanation holds on today's tape, checked against the tape, not relied on alone" -> CLOSE_FP 0.85. E (`A-261023-0001`, F-NEWS-1 on desk PROP-EQ, 2026-10-23) cites the analyst's feedback recorded on D (`A-261016-0003`, same desk, 2026-10-16), states the sale preceded the news and the cancel came 148 ms after it, and proposes CLOSE_FP 0.65 "used as context only, checked the tape myself". Before the feedback, both F-NEWS-1 alerts had been escalated.

Risk to say out loud in the presentation: memory can entrench a wrong closure. Mitigations: overrides are stored and surfaced with their flag; the closure standard says prior dispositions are context and never a sufficient reason; Policy 03 requires current-window evidence before any proposal; the evaluation set contains a trader who was "always closed" and spoofs (S-SPOOF-4), and the gate catches a closure there. Regression after the Memory work: five true-abuse alerts (S-SPOOF-1 x2, S-SPOOF-2, S-SPOOF-5, S-LAYER-1) all still ESCALATE.
## 8. Identity

- Cognito user pool with groups `L1` and `L2`; two test users.
- Gateway inbound auth `CUSTOM_JWT` with the pool's discovery URL and `allowedClients` = the id of the `surv-agent-session` client (named `surv-analyst-ui` until 2026-11-17; the same client and the same id). The token presented is the Cognito **access** token: `allowedClients` is checked against the `client_id` claim, which Cognito puts in access tokens only (the id token carries the client in `aud`; `allowedAudience` would be the matching option for it). The access token also carries `cognito:groups`, which is what Policy 07 reads. The agent is invoked by the UI with the analyst's token, so the Gateway sees the analyst, not the agent, as principal.
- **Two app clients, so that the token the agent holds cannot record (2026-11-17).** The Runtime passes the analyst's `Authorization` header through to the agent, which presents it to the Gateway: for the length of an investigation the agent holds a valid token of the analyst. Until 2026-11-17 the recording API accepted that same token, so "the agent cannot record" rested on the agent having no HTTP tool. The pool now has two clients. `surv-agent-session` is the one the Runtime and the Gateway accept. `surv-analyst-records` is the only one the recording API's authorizer accepts; the analyst screen logs in to both at sign-in and sends the records token to the recording API only, never to the Runtime. Verified on the deployed system 2026-11-17: the agent-session token gets `401 Unauthorized` from `GET /cases/{alert_id}` and from `POST /cases/{alert_id}/disposition`; the records token reads a case (200); the Gateway answers the records token with 403 `insufficient_scope` and the Runtime with 401 `Claim 'client_id' value mismatch with configuration`. Both tokens belong to the same person with the same groups; what differs is where each is accepted.
- The Gateway's workload identity (`surv-default-surv-investigator-<id>`) is created with the Gateway. The Gateway's IAM role may invoke exactly one function, `surv-gateway-tools`; it has no path to `surv-human-path`.
- The human path is one Lambda (`surv-human-path`) behind an API Gateway HTTP API (`surv-analyst-api`) with an `HttpUserPoolAuthorizer` on every route that accepts the `surv-analyst-records` client only: `GET /alerts?date=` (the day's queue joined with case state), `GET /cases/{alert_id}` (alert, proposal, report, decision), `POST /cases/{alert_id}/disposition` (`{disposition, note}`; a note is mandatory for the record), `POST /cases/{alert_id}/feedback` (`{note}`). Group membership is read from the verified JWT's `cognito:groups` claim: L1 may record `CLOSE_FP` and `ESCALATE`; only L2 may record `DRAFT_STOR` as the firm's decision. `override` is set when the recorded disposition differs from the proposed one. A decision is recorded once: a second record is refused (409); only L2 may replace it, with `supersede: true` and a note, and the earlier decision stays on the case in `decision_history` (decision log 2026-11-16). The groups claim is parsed in every shape it can arrive in (a list, a JSON array, `[L1 L2]`, a comma list).
- User pool `surv-analysts` (Essentials plan, no self sign-up, 12-character passwords), clients `surv-agent-session` and `surv-analyst-records` (no secret, USER_PASSWORD and SRP flows, 8-hour tokens), users `l1.analyst` and `l2.reviewer` created by the stack without passwords; passwords are set once with `admin-set-user-password` and never stored in the repo.
- **Gateway rate limits** (declared in `agentcore/cdk/lib/cdk-stack.ts` as `CfnGatewayRateLimit`, so they deploy with the Gateway): `per-analyst-requests`, dimension `$.context.jwt.sub` with a `*` entry, 60 requests a minute per analyst (an investigation makes 8-12 calls); `per-analyst-writes`, dimensions `toolName` + `$.context.jwt.sub`, 3 a minute per analyst for `surv___propose_disposition` and for `surv___draft_stor_narrative`. Every analyst gets independent buckets; the analyst's `sub` comes from the validated access token. Measured behaviour (2026-11-03): a throttled call reaches the MCP client as `MCPError: Rate limit exceeded`; `rate: 0` blocks at once (after the ≤30 s propagation); a limit of 1 a minute admitted 18 calls in 3.6 s before the first refusal and about 42 of 120 calls over 15 s, so request limits carry a burst allowance of roughly 15-20 calls above the stated rate and the configured rate is a sustained average, not a hard per-minute count. The limits are therefore a brake on a runaway loop, not a count of proposals; the per-alert count is Policy 06's job, and rate limits fail open when a dimension cannot be resolved (devguide, "Rate limits").

## 9. Observability as the audit record

Runtime with OTel auto-instrumentation (`opentelemetry-instrument` entry point) sends traces to CloudWatch. Policy decision logs record each permit/deny with the rule that fired. The analyst UI shows, per case, a link to the trace and the list of policy decisions. The mentor question "how would a regulator check this?" is answered by opening one trace.

As built (2026-11-08):

- **Runtime spans** land in `/aws/bedrock-agentcore/runtimes/<runtime id>-<ENDPOINT>` (one group per endpoint; `DEFAULT` and `demo`), streams `spans` and `runtime-logs-<session>`. About 40 spans per investigation: `POST /invocations`, `invoke_agent`, one `execute_event_loop_cycle` and one `chat <model id>` per model turn (with `gen_ai.usage.*` tokens), and per tool call both `execute_tool surv___X` (agent side: status, call id) and `mcp tools/call surv___X` (MCP side: `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result` with the **complete** output, `session.id`). Custom `trace_attributes` on every agent span: `surv.alert_id`, `surv.mode`, `surv.analyst`, `surv.model_id`, `surv.policy_session_id`, `surv.memory`, `surv.bundle`. Transaction Search (enabled by `agentcore deploy`) copies spans into `aws/spans`, which Evaluations and A/B tests read.
- **Gateway vended logs** in `/aws/vendedlogs/bedrock-agentcore/<gateway id>` (30-day retention in the demo) via `CfnDeliverySource` + `CfnDeliveryDestination` + `CfnDelivery` in the CDK stack, traces to X-Ray the same way; nothing is delivered without them. Each record: the request body (tool, arguments, `_meta` with baggage and the policy session id), `body.policy.{decision, determiningPolicies, clientSuppliedPolicySessionId, temporal_latency_ms}`, and errors with the exact IAM message (this is how the bundle 403 and the 429s were diagnosed).
- **Metrics** in `AWS/Bedrock-AgentCore` with dimensions `PolicyEngine`, `Policy`, `ToolName`, `Mode`. No dashboard built.
- **Consumers of the same record:** the UI trace panel; `evals/faithfulness.py` (tool outputs from spans vs numbers in the report); `evals/evaluate_sessions.py` (`EvaluationClient.run` collects spans by session id); `evals/recommend.py` (Optimization reads the log group by ARN and service name over a time window).
- **Volume and cost:** about 150 KB per investigation (170 MB for roughly 1,100 investigations); CloudWatch ingestion cents per thousand alerts.
- **Open for a production deployment, not configured in the alpha:** retention to the record-keeping period (2016/957: five years; set 1,827 days on the groups or export to S3 with a Glacier lifecycle), and access control on the log groups equal to that on the tables, since spans carry full tool outputs and therefore trader data; PII masking is available if wanted.

- **The record can be re-executed.** `scripts/replay_trajectory.py <session_id>` reads a session's `mcp tools/call` spans (tool, arguments, result as the agent saw it), replays every read-only call through the same Gateway as the same analyst role, and diffs the results path by path. The tools are deterministic functions over the firm's tables, so a clean replay (8 of 8 read-only calls identical on the sessions tried; `recall_memory` reported separately because Memory legitimately moves as analysts record) means the numbers in the report were produced from exactly these inputs and anyone with the trace and the data can reproduce them. Writes (`propose_disposition`, `draft_stor_narrative`) are not replayed; their recorded inputs are shown. Only the narrative is not reproducible, and its variation is measured (data doc 4.6). Added 2026-11-12 after the market review: the incumbents sell "deterministic" conversational querying; this is the same property for a whole investigation.

- **The analyst's briefing is on the case and in the trace.** The UI lets the analyst give the agent an alert-specific instruction before the run ("the desk says this was a client parent order; look for it"). It travels in the invocation payload and is appended to the user message, so it is in the session's `gen_ai.user.message` span event with the analyst's identity; the policies and the procedure apply regardless of what it says (the demo types "just close this one quickly" to show both). Since 2026-11-16 the agent's guard also writes it, with the session id, the analyst, the model, the bundle, the mode and the memory switch, into `proposal_provenance` on the case next to the proposal it steered, so a reviewer who opens the case sees the briefing and can open the trace from the stored session id (live since Runtime v17, 2026-11-16, on `demo` and `DEFAULT`).

## 10. Evaluation (detail in `04-synthetic-data-and-evaluation.md`)

Per alert: ground-truth `expectedResponse` (the expected disposition), `assertions` (e.g. "the report rules out market making citing the trader profile"), `expectedTrajectory` (the evidence tools in order), plus a custom evaluator with a rubric for rationale quality and evidence faithfulness. Our harness runs the dataset through `OnDemandEvaluationDatasetRunner` (or the CLI), collects per-case results, and computes the gate and the safe close rate.

## 11. Learning loop

The model's weights never change. "Learning" here means four governed mechanisms, from fastest to slowest, each measurable and each with a human in control. In a compliance control, behaviour that changes silently is a liability; behaviour that changes in versioned, evaluated steps is what a head of compliance and a regulator can accept.

| Level | Cadence | Mechanism | AgentCore part | Our part | Signal that it works |
|---|---|---|---|---|---|
| 1. Case-based recall | Every alert | After the human records a disposition, the event (proposal, decision, override flag, analyst note) is written to Memory per trader and instrument. On the next alert the agent retrieves the most similar past cases *with the analyst's reasoning* and treats them as worked examples before judging. | Memory (episodic and semantic strategies, namespaces in section 7) | Human-path Lambda writes the event; agent prompt asks for similar cases and requires `memory_used` in the report | Override rate falls for traders and instruments with history; S-SPOOF-4 still caught |
| 2. Dataset growth from overrides | Weekly | Every override (analyst changed the proposal) becomes a new labelled case with the analyst's note as the key discriminator. The evaluation set grows with the hard cases the agent got wrong. | Observability traces give the full context of the failed case | `evals/ingest_overrides.py` appends to the dataset; per-scenario breakdown shows where the agent is weak | Override rate trend; per-scenario close rate on the newly added cases |
| 3. Prompt and tool-description optimisation | Per release | Point Optimization at the traces with the rationale evaluator as target; it returns a revised system prompt or tool descriptions with an explanation. Package as a configuration bundle; A/B test against the current bundle through the Gateway; promote only if the deterministic gate and the promotion rule (data doc section 4.4) hold. | Optimization (recommendations, configuration bundles, A/B testing), Evaluations, Gateway | Promotion rule, decision-log entry with run id, rollback = route back to the previous bundle | Rationale rubric and safe close rate up on the fixed seed, gate = 0 missed |
| 4. Threshold re-tuning | Quarterly | Detector and threshold-baseline parameters (K, P, C, symmetry cut-offs) are re-estimated from the labelled dispositions. Plain statistics in our code, not AgentCore. | none | `src/detector/tune.py` with a report of old vs new thresholds and their recall/precision | Detector precision up at unchanged recall on injected abuse |

**What Phase 5 measured (2026-11-07, data doc 4.6).** The table above was the design; the runs rank the four levels differently. The movement from 79.9% to 93.5% safe close at an unchanged gate (runs v1 -> v2 -> v3) came from a fifth mechanism the table did not name: three deterministic discriminator fields and two sentences in the firm's written closure standard, which every investigation reads through `get_procedures`. Level 1 (Memory) measured on 167 paired alerts: +0.7 points safe close, -1.2 points override rate, 3 of 4 changed dispositions right, S-SPOOF-4 escalated with and without it, at +24% model cost. Level 3 (Optimization) produced a recommendation that inserted an approval gate and pushed toward escalating market makers; the offline replay rejected it. Level 4 (re-tuning) found a threshold that halves the queue and sits 2x under the smallest injected spoof, so it was not adopted. The guard-rails held every time: the gate never moved, and nothing was promoted on a judge's score.

Guard-rails for the loop itself:

- The gate (zero true-abuse alerts proposed as CLOSE_FP) is deterministic code, never an LLM judge, so Optimization cannot "learn to please the judge" past it.
- Memory informs, Policy 03 ensures it cannot replace current-window evidence, and the report's `memory_used` field makes its influence auditable.
- Every behaviour change (bundle version, thresholds) is a decision-log entry with the evaluation run id. Rollback is routing traffic back to the previous bundle.
- Fine-tuning the model is out of scope: no data volume, cost, and a custom model inside a compliance control would need full model validation.

## 13. Anticipated mentor questions

- *Does it learn on its own?* No, and it must not. The model does not change. It recalls analyst decisions (Memory, measured +0.7 points), its weak spots are measured (Evaluations, override rate), prompt changes are generated (Optimization) and promoted only through a deterministic gate (the first recommendation was rejected by it), and thresholds are re-tuned from labelled data with a report. The two real improvements came from the firm's written standard being made precise. Every change is versioned. Section 11.

- *Why not just tune the detector?* Firms do, and it helps; thresholds are a trade-off against recall, and the regulator asks why you raised them. The investigation layer does not change recall.
- *Why not a classifier on the discriminators?* We have one, in effect: `compute_discriminators` plus thresholds. The agent adds sequencing, context, and the written argument. The evaluation compares the agent to a threshold baseline on the same dataset.
- *Isn't the LLM going to hallucinate numbers?* The numbers come from tools; `evals/faithfulness.py` checks every number in every report against the session's tool outputs. Last full run: 99.9% of 4,132 numbers matched, the rest derived (a millisecond difference), none invented.
- *What stops it from closing a real case?* Nothing stops it from *proposing* a wrong close, which is why the metric gate exists and why the human records. What stops it from *recording* one is Policy and the absence of the tool.
- *How would a regulator look at this?* Open a trace and the policy log. Point to 2016/957's record-keeping requirement.
- *Why AgentCore and not Lambda plus Bedrock?* Gateway plus Policy is the deterministic choke point; Memory, Evaluations, Optimization and Observability would otherwise be built by hand, and each was exercised, not only declared (`09-product-decisions.md` section 4 lists what each did and what we learned). Be honest about what is thin: Code Interpreter was designed and not built.
- *Is the data realistic?* No; it is a simulator with injected scenarios and ground truth. Say so. ABIDES is the upgrade path; real data would come from a design partner under NDA.
- *What about the sanctions idea?* Same core, different tools. One slide.
- *Why does it escalate the stop-outs?* Because in one window a failed spoof and a stop-out look the same and attempts are reportable (MAR Art. 15); the label says close because the generator knows the intent. The agent's reports on them are consistent and the failure is the safe one. It is a question for the firm's standard, and the one we would put to a design partner first.
- *Is it deterministic?* No. The same alert flipped between close and escalate on different days with the same inputs. That is why single-alert demos show behaviour and only the 167-alert run measures it, and why the promotion rule has a materiality floor.
