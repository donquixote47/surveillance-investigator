Carried over from the earlier sanctions project (checked against the developer guide in September 2026) and re-checked where marked. The service changes monthly: when in doubt, re-check with the `aws-agentcore` power (`search_agentcore_docs`, `fetch_agentcore_doc`) before asserting anything, then update this file with the date.

## Service inventory [verified 2026-11-02, devguide "What is Amazon Bedrock AgentCore?"]

Harness, Runtime, Memory, Gateway, Identity, Code Interpreter, Browser, Observability, Payments, Evaluations, Optimization, Policy, Registry. All listed as services in the overview; none flagged as preview there. ## Naming and identifiers [checked 2026-09, re-verify in Phase 0]

- Gateway exposes a target's tools as `${target_name}___${tool_name}` (three underscores). Our target is `surv`, so the MCP tool is `surv___get_alert` and the policy action is `AgentCore::Action::"surv___get_alert"`.
- Runtime, Memory, Policy Engine and Policy names: `[a-zA-Z][a-zA-Z0-9_]{0,47}`. Gateway and target names: `([0-9a-zA-Z][-]?){1,100}`.
- Runtime `runtime_session_id` must be 33-256 characters; reuse it for multi-turn conversations.

## Policy (Dogwood, Cedar-compatible) [rewritten 2026-11-04 after deploying nine policies and probing them]
- **LOG_ONLY does not record `::response` events.** Ten probe variants in one session: every `::response`-based predicate denied after its prerequisite had completed, every `::request`-based one allowed; the same sequence with the engine attached in `ENFORCE` behaved as designed. Temporal rules that depend on responses can only be tested in `ENFORCE` (on a disposable alert). Do not plan a LOG_ONLY observation period for them.
- Validation is against a Cedar schema generated from the Gateway's tool manifest: a policy cannot name a tool that does not exist (`unrecognized action`), and a policy whose resource is `resource is AgentCore::Gateway` does not bind the manifest at all (every tool name "unrecognized"). Name specific actions only with `resource == <gateway ARN>`.
- Every `forbid` trips the "Overly Restrictive: Policy Engine will deny every request for ..." finding because validation does not see the sibling permits. Declare forbids with `validationMode: IGNORE_ALL_FINDINGS`; keep permits on `FAIL_ON_ANY_FINDINGS`. A failed policy rolls back the whole `AgentCore-surv-default` stack; one 13 KB finding exceeded CloudFormation's 2 KB status field. `scripts/validate_policies.py` shows the findings before a deploy.
- Quotas that bit: 3 temporal operators per policy (03 split into 03a/03b), 20 temporal policies per engine, 24 h max window. Every predicate must carry `eventResource: resource`. Ordered comparisons need `Long`; `==` works on any type (that is how `input.alert_id: context.input.alert_id` correlates).
- Session header `x-amzn-bedrock-agentcore-policy-session-id` on every Gateway call; with a temporal policy on the engine, a call without it fails validation. The Gateway role needs `bedrock-agentcore:GetWorkloadAccessToken` on `workload-identity-directory/default` and `.../workload-identity/<gateway id>*`; the CLI's generated role lacks it (`Failed to get workload identity token ... not authorized`). Granting it in the CDK stack with `gateway.gatewayId` creates a role<->gateway cycle; use the known name prefix.
- Adding or updating a temporal policy invalidates open policy sessions (409 on reuse). Policies are asynchronous (status CREATING -> ACTIVE/CREATE_FAILED, `statusReasons`).
- JWT claims are string tags on `AgentCore::OAuthUser`; Cognito's `cognito:groups` array arrives as the text `["L2"]`, so match with `like "*L2*"`. `tools/list` for a principal omits tools a forbid denies (`PartiallyAuthorizeActions`): an L1 token sees 10 tools, L2 sees 11.
- Denials reach the MCP client as `MCPError: Tool Execution Denied: Tool call not allowed due to policy enforcement [Policy evaluation denied due to <policy id>]`. When several policies would deny, the forbid is reported (03b before 03a).
- Observability: Gateway logs and traces are vended logs; nothing is delivered until a `CfnDeliverySource` (`APPLICATION_LOGS`, `TRACES`) + `CfnDeliveryDestination` (CWL / XRAY) + `CfnDelivery` pair exists. Log records carry `body.policy.{decision, determiningPolicies, clientSuppliedPolicySessionId, temporal_latency_ms}`; temporal evaluation adds 30-60 ms. Metrics in `AWS/Bedrock-AgentCore` with dimensions `PolicyEngine`, `Policy`, `ToolName`, `Mode`.
- Earlier notes still valid (checked 2026-09):

- Deny by default. A tool call is allowed only if a `permit` applies and no `forbid` overrides it. `forbid` always wins.
- Temporal conditions live in a `temporal { ... }` block and look back over the *policy session*. Events referenced: `::request` (a call was made), `::response` (a call completed and was permitted), `::error` (a call was denied).
- A `::response` event is recorded only for permitted calls. The agent must await each tool result before issuing the dependent call. Strands does this sequentially by default; do not parallelise prerequisite and dependent calls.
- Because deny-by-default, every prerequisite tool needs its own plain `permit`, otherwise it is never recorded as a response and the dependent rule can never fire.
- Self-referential rules (cool-down) must match on `::response`, not `::request`, or the current request matches its own event.
- Session-scoped counts are resettable by starting a new session. Present them as behaviour shaping, not as hard security. Pair with identity-scoped Gateway rate limits.
- Per-policy enforcement mode `LOG_ONLY` vs `ACTIVE` exists: test on real traffic first, read decision logs, then switch. [verified 2026-11-02, "Test a policy in LOG_ONLY mode"]
- Policy creation is asynchronous; validation runs against the Cedar schema derived from the Gateway's tools, so the Gateway target must exist and be READY before policies referencing its tools can validate.
- Natural-language policy generation exists and validates per policy. Use it once as a demo, hand-write the rest. [verified 2026-11-02, "Policy generation: per-policy validation"]
- Dogwood is open source (github.com/dogwood-policy/dogwood). Useful for testing policies locally.

## Gateway [checked 2026-09]

- `searchType: SEMANTIC` cannot be changed after creation.
- `UpdateGateway` replaces all fields; fetch first and pass existing values through.
- Inbound auth: `CUSTOM_JWT` (Cognito) or `AWS_IAM`. Never `NONE` here.
- Lambda targets need a `toolSchema` with input *and output* schemas. Temporal policies reference `output.<field>` of prior responses, so declare `alert_id`, `trader_id`, `disposition`, `evidence_ids` in the schemas.
- Per-user rate limiting is configured on the Gateway [verified 2026-11-03 by probing]: `CreateGatewayRateLimit` / `BatchPutGatewayRateLimits` (upsert) with `dimensionKeys` from {`targetName`, `toolName` (= `target___tool`), `$.context.jwt.<claim>`, `$.context.iam.principal`, header/body selectors} and `entries` (`*` = per-entity buckets, trailing positions only). CloudFormation `AWS::BedrockAgentCore::GatewayRateLimit` exists (L1 `aws_bedrockagentcore.CfnGatewayRateLimit` in aws-cdk-lib ≥ 2.269; not taggable). Throttled MCP call surfaces as `MCPError: Rate limit exceeded`. **Request limits have a burst allowance**: at 1/min, 18 calls passed before the first refusal and ~42 of 120 in 15 s; `rate: 0` blocks outright. Treat the rate as a sustained average; counting belongs to Policy. Propagation ≤ 30 s; fail-open when a dimension does not resolve.
- Up to two Lambda interceptors (REQUEST, RESPONSE): an alternative place for audit logging.
- Lambda target contract [verified 2026-11-02, devguide "Lambda functions" for Gateway targets]: the Lambda receives the tool's input properties as the `event` (no envelope) and the full tool name `<target>___<tool>` in `context.client_context.custom['bedrockAgentCoreToolName']`. One Lambda ARN per target, one tool schema per target: dispatch inside the function (`src/tools/lambda_handlers/gateway_tools.py`). Locally we pass `__tool__` in the event instead.
- Tagging [verified 2026-11-03 against the installed boto3 model]: `tags` on `CreateGateway`, `CreateAgentRuntime`, `CreateMemory`, `CreatePolicyEngine`, `CreateCodeInterpreter`, `CreateEvaluator`; `TagResource` and `ListTagsForResource` are on the **control-plane** client (`aws bedrock-agentcore-control tag-resource`), not on `bedrock-agentcore`. Built-in evaluators have account-less ARNs (`arn:aws:bedrock-agentcore:::evaluator/...`) and cannot be tagged. `scripts/check_tags.py` audits everything.

## Runtime [checked 2026-09]

- Isolated microVM per session; billed for active session time. Default idle timeout 900 s, max lifetime 28800 s. Stop sessions after demos.
- Each update creates an immutable version; the DEFAULT endpoint moves to the newest. Pin a `demo` endpoint to a known-good version before presenting.
- Protocols: HTTP, MCP, A2A. Our L1 agent is HTTP; a stretch L2 reviewer agent would be A2A.
- Direct code deployment for Python (zip) exists as an alternative to containers. [verified 2026-11-02, "Direct code deployment for Python"]

## Runtime, learned by deploying [verified 2026-11-03]
- CLI layout: `agentcore add runtime --name X --language python` writes only `app/X/README.md` + `AGENTS.md`; the code is ours: `app/X/main.py` (module-level `app = BedrockAgentCoreApp()`, `@app.entrypoint def invoke(payload, context)`, `app.run()` under `__main__`) and `app/X/pyproject.toml` (`[project].dependencies` is the only place deps are read from; `requires-python` constrains `runtimeVersion`; `[tool.agentcore] entrypoint`). No Dockerfile = CodeZip (direct code deploy; aarch64 wheels only, glibc ≤ 2.34, zip < 250 MiB). `findManifest` walks up from `codeLocation` to the project root, so a runtime folder without its own `pyproject.toml` silently inherits the root one.
- The CLI's generated `agentcore/cdk/tsconfig.json` uses `moduleResolution: "Node"` (node10), which TypeScript 6 (the IDE's) reports as deprecated. We set `module`/`moduleResolution` to `Node16`; output stays CommonJS (no `"type": "module"` in package.json). TypeScript 7.0.2 (2026-11-03) additionally needs `"types": ["node"]`: it no longer includes `@types/*` from `typeRoots` automatically (`Cannot find name 'console'/'process'`). `@aws/agentcore-cdk` 1.0.1 peers on `aws-cdk-lib ^2.269.0`, so the CLI stack runs the same 2.275.0 as `infra/`. `agentcore add ...` rewrites `agentcore.json`, not the tsconfig, so the change sticks. [2026-11-03]
- Deployed names are `<project>_<target>_<runtime>`: ours is `surv_default_surv_investigator_l1`. Entry point becomes `opentelemetry-instrument main.py`. The CLI injects `AGENTCORE_GATEWAY_<NAME>_URL/_ARN/_AUTH_TYPE` for every project Gateway; a `protocolType: None` Gateway URL is a bare origin, append `/mcp`.
- Analyst-token passthrough: Runtime `authorizerType: CUSTOM_JWT` + `requestHeaderAllowlist: ["Authorization"]`; the SDK exposes it as `context.request_headers["Authorization"]` (normalised key). Invocation with CUSTOM_JWT is plain HTTPS, no SigV4: `POST https://bedrock-agentcore.<region>.amazonaws.com/runtimes/<url-encoded ARN>/invocations?qualifier=DEFAULT` with `Authorization: Bearer <access token>` and `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` (33+ chars). `scripts/invoke_runtime.py` is the reference. 35 s wall for a 9-tool investigation, 7 s for a refused request (cold start included).
- Observability: spans land in the Runtime's log group `/aws/bedrock-agentcore/runtimes/<id>-DEFAULT`, stream `spans` (not only in `aws/spans`); one span per `execute_tool` and `mcp tools/call`, plus `chat <model>` per model call; `trace_attributes` passed to the Strands `Agent` appear as span attributes (`surv.alert_id`). Per-session streams `runtime-logs-<session id>` hold the app logs.
- Strands + MCP: `MCPClient(url=..., headers={"Authorization": ...})` as a ToolProvider in `Agent(tools=[mcp])`; the Agent starts it, `agent.cleanup()` stops it; wrapping it in `with mcp:` as well raises "client session is currently running". `BeforeToolCallEvent.cancel_tool = "<message>"` turns the call into an error tool result the model reads. `SequentialToolExecutor` keeps calls in order (the model still batches several `toolUse` blocks in one message; they execute one by one).
- Claude 5.5 on Bedrock [Bedrock user guide, 2026-11-03]: `temperature` -> ValidationException ("deprecated for this model"); adaptive thinking is on by default (Sonnet/Opus effort `high`, Haiku `medium`) and its tokens count against `max_tokens`; set `additional_request_fields={"thinking": {"type": "adaptive"}, "output_config": {"effort": ...}}`; `thinking.type: "enabled"` with `budget_tokens` is rejected. We use `max_tokens=32000`, effort `medium`. Strands raises `MaxTokensReachedException` and leaves the partial assistant message in `agent.messages`.

## Memory [rewritten 2026-11-05 after building it]
- `BatchCreateMemoryRecords` writes records directly (no strategy, immediate, `metadata` map of typed values); `RetrieveMemoryRecords` is semantic search over one namespace with `score`. Records the SEMANTIC strategy extracted from `CreateEvent` land in the same namespace and carry `x-amz-agentcore-memory-strategyType != NONE`; direct ones say `NONE`. Extraction from a one-sentence feedback took under a minute and produced two facts.
- Namespace regex on the data plane is `[a-zA-Z0-9/*][a-zA-Z0-9-_/*]*...`: no dots (`SYN.A` must become `SYN_A`), and `RetrieveMemoryRecords`/`ListMemoryRecords` reject the trailing slash that the docs recommend and that `BatchCreateMemoryRecords` accepts. Strip it on read.
- The Lambda `python3.14` runtime's bundled boto3 did not know `metadata` on memory records (`Unknown parameter in records[0]: "metadata"`); ship a current boto3 in the layer. Lambdas need `bedrock-agentcore:RetrieveMemoryRecords` (read) and `BatchCreateMemoryRecords`, `CreateEvent`, `UpdateMemoryRecordExpirySpecification` (write) on the memory ARN.
- The CLI injects `MEMORY_<NAME>_ID/_ARN` into Runtimes only; Lambdas in another stack get the id by CDK context (`-c memoryId=...`, persisted in `infra/cdk.json`).
- Adding a Gateway tool whose name a policy uses needs two deploys: target first (new manifest), then the policies that name it; otherwise `unrecognized action` rolls the stack back.
- Earlier notes (2026-09): strategies semantic, summary, user preference, episodic, custom; long-term extraction asynchronous; `CreateEvent` accepts a `json` payload; plan namespaces first; semantic retrieval billed per call.

- Strategies: semantic, summary, user preference, episodic, custom. Long-term extraction is asynchronous; expect delay before records are retrievable.
- `CreateEvent` accepts a `json` payload for non-conversational data. This is how disposition events are stored.
- Plan the namespace scheme before creating the resource (per trader, per instrument, per analyst); awkward to change later.
- Semantic retrieval is billed per call.

## Evaluations [verified 2026-11-02, "Ground truth evaluations"]

- Ground truth is supported: `Builtin.Correctness` (trace-level, `expectedResponse`), `Builtin.GoalSuccessRate` (session-level, natural-language `assertions`), `Builtin.TrajectoryExactOrderMatch` / `InOrderMatch` / `AnyOrderMatch` (session-level, `expectedTrajectory.toolNames`, programmatic, no LLM cost).
- Custom evaluators can use placeholders `{assertions}`, `{expected_response}`, `{expected_tool_trajectory}`, `{actual_tool_trajectory}`, `{available_tools}`, `{context}`, `{assistant_turn}`. Custom evaluators with ground-truth placeholders cannot run in online mode.
- Prerequisites: agent on Runtime with observability enabled (or Strands/LangGraph instrumented with OTel), CloudWatch Transaction Search, 2-5 minutes for telemetry ingestion before evaluating.
- `OnDemandEvaluationDatasetRunner` runs the full loop (invoke, wait, collect spans, evaluate) client-side. Also `agentcore eval ondemand evaluate` in the CLI.
- Evaluations scores sessions and traces individually. The project's aggregate metric (safe close rate at 100% recall) is computed by our own harness over the per-case results. Don't claim Evaluations computes it.
- [verified 2026-11-05 on live sessions] `bedrock_agentcore.evaluation.EvaluationClient.run(evaluator_ids, session_id, log_group_name, reference_inputs=ReferenceInputs(...))` scores a session that already ran (no re-invocation): it collects the spans from the Runtime log group and calls `Evaluate` per evaluator level. `OnDemandEvaluationDatasetRunner` is only needed when Evaluations should also drive the invocations. Our harness invokes (`evals/run_dataset.py`) and then scores (`evals/evaluate_sessions.py`).
- Tool names in the spans and in `actual_tool_trajectory` carry the Gateway target prefix: `surv___get_alert`. `expected_trajectory` must use the same names or every trajectory evaluator returns 0 with "not found in order".
- Judge token usage per session here: `Builtin.GoalSuccessRate` ~23k in (reads the whole session), `Builtin.Correctness` ~1k, the custom rubric on Opus 5.5 ~12k in / 1.5k out. Trajectory evaluators are programmatic (no `tokenUsage`). Prices (pricing page 2026-11-05): built-in LLM evaluators $2.40 / $12.00 per M tokens in/out, model included; custom evaluators $1.50 per 1,000 evaluations plus the judge model's tokens in the account; batch evaluations 25% off.
- `Evaluate` results carry `evaluatorId`, `evaluatorName`, `value`, `label`, `explanation`, `context.spanContext`, `tokenUsage`, `ignoredReferenceInputFields` (e.g. Correctness ignores `assertions`). Custom evaluators return `evaluatorId` = `<name>-<suffix>`.
- Multi-dimension custom evaluators are **not** supported in A/B tests or in Optimization recommendations. The rationale rubric is a single numerical scale (0, 0.25, 0.5, 0.75, 1) with the four points in the instruction for that reason; it also uses no ground-truth placeholder so it can run online.
- `agentcore add evaluator llm-as-a-judge` fixes the judge to `temperature 0` / `maxTokens 4096` and accepts integer rating values only; Claude 5.5 rejects `temperature`. Custom evaluators are therefore created with `create_evaluator` from `evals/evaluators/*.json` (`uv run evals/evaluators.py create <name>`), with `tags` on creation. Status enum: CREATING, ACTIVE, CREATE_FAILED, UPDATING, UPDATE_FAILED, DELETING; creation took a few seconds.
- The judge model id `eu.anthropic.claude-opus-5-5` in `bedrockEvaluatorModelConfig` (no `temperature`, `maxTokens` 3000) is accepted and answers in ~20 s per session.
- Judge calls from this machine can fail with `EndpointConnectionError` during a long pass (network stall, not throttling); `evals/evaluate_sessions.py --alerts ...` re-scores single sessions and the aggregate is rebuilt from the saved files.

## Throttling in a dataset run [observed 2026-11-06]
- Two concurrent investigations by the same analyst (same JWT `sub`) touch the Gateway's 60-requests-per-minute burst: 6 of 167 invocations in run v2 got a Gateway 429 mid-investigation. The Strands `MCPClient` does not retry; the 429 surfaces as `Connection to the MCP server was closed`, the Runtime invocation fails with 500, and the HTTPS invocation endpoint returns **HTTP 424** `Received error (500) from runtime`. `evals/run_dataset.py` treats 424/429/5xx as transient (one retry after 90 s) and `--resume --retry-errors` re-runs the leftovers; two arms run at concurrency 1 each are the safe way to run in parallel. A retry inside the agent's MCP client would be the proper fix.

- Fixed in Runtime v12 (2026-11-07): the agent's MCP client now uses a transport that retries 429/503 with back-off (`RetryOn429` in `investigator.py`, honours Retry-After). The Runtime bundle resolves **mcp 1.30 + httpx 0.28** while this machine has **mcp 2.3 + httpx2**; `strands.tools.mcp._compat.MCP_V2` tells which, and the transport is built either with `streamable_http_client(url, http_client=httpx2.AsyncClient(transport=...))` (2.x) or `streamablehttp_client(url, headers, httpx_client_factory=...)` (1.x). An unconditional `import httpx2` deployed as v11 and failed every invocation with `ModuleNotFoundError` in ~31 s (HTTP 424); always check `agentcore/.cache/<runtime>/staging/*.dist-info` for what the Runtime really gets.
- [observed 2026-11-17, run `20261117T1255-seed9-mm`] The retry does not make throttling impossible. One of 48 investigations failed twice at concurrency 2 with `429 Too Many Requests` from the Gateway's MCP endpoint in the Runtime's stack trace (`ToolProviderException: Failed to cleanup MCP client: Connection to the MCP server was closed`, HTTP 424 to the caller), about 40 s in, before any proposal was written; `--resume --retry-errors` completed it. The cause first written here was wrong (two slots near the 60-requests-a-minute limit). Established 2026-11-18: it is the write limit, 3 proposals a minute per analyst, met by the proposal itself (see "The Gateway throttle, traced" below). The same day, 72 investigations at `--concurrency 1` ran with none throttled. The Runtime's app logs are in streams named `YYYY/MM/DD/[runtime-logs-<session id>]<uuid>`, not `runtime-logs-<session id>`: filter the group by the alert id.
- Opus 5.5 passed `report` to `propose_disposition` as a JSON **string** in 5 of 167 runs; `dict(str)` inside the guard hook raised `ValueError: dictionary update sequence element #0 has length 1` and the whole investigation died (`EventLoopException`). The guard now parses a string and rejects anything that is not an object with a message the model can act on.
- Sonnet 5.5 wrote `ruled_out` for the report field `ruled_out_by` in 24 of 167 v3 sessions (`extra="forbid"` rejected it, full rewrite each time, +8.6 s / +32k tokens). Shapes seen: the key alone, and (Runtime v13, 2026-11-10) **both keys at once** with the declared one empty, which a pydantic `AliasChoices` does not cover (the second key is still "extra"). A `model_validator(mode="before")` that folds the legacy key into the declared one handles every shape; test both-keys-at-once whenever you alias a field on a model with `extra="forbid"`.

- Moving an endpoint alias (release/rollback) [verified 2026-11-10]: `agentcore add runtime-endpoint` refuses an existing name ("already exists"); the alias version lives in `agentcore.json` `runtimes[].endpoints.<name>.version` and is applied by `agentcore deploy` through the CDK stack. A deploy cuts a new Runtime version only when the agent artefact changed (the 2026-11-11 alias move also carried a changed zip and gave v15; the 2026-11-12 alias move did not and gave no version, so `demo` = `DEFAULT` = 16; the 2026-11-16 move to v17 did not either, `demo` = `DEFAULT` = 17; on 2026-11-17 a deploy with no change to the agent cut v18 from a boto3 patch release, `demo` = 17, `DEFAULT` = 18, see the 2026-11-17 section). Editing that one field is the CLI's own mechanism, not a bypass of it.

## Prompt caching on Bedrock through Strands [verified 2026-11-10 on Runtime v13/v14]
- `BedrockModel(cache_config=CacheConfig(tools_ttl=True))` (strands-agents 1.63/1.64; `strands.models.model.CacheConfig`) places cache points at the end of the system prompt, on the tool block and on the last user message. `tools_ttl` must be set explicitly: the default `None` defers to the deprecated `cache_tools` and caches no tools. `strategy="auto"` resolves to "anthropic" for any id containing "claude" or "anthropic", so the `eu.` inference-profile id works without a model-info entry.
- Works on the cross-region `eu.` profile: on one Sonnet 5.5 investigation (5 model turns) `inputTokens` dropped from 91,595 to **12**, with 62,957 `cacheReadInputTokens` and 28,638 `cacheWriteInputTokens` (the user guide's warning that cross-region "may lead to increased cache writes" did not show at this volume). Over 30 alerts: 73.5% of prompt tokens read from cache, 26.5% written, ~11 at full price; estimated model cost -52% at 0.1x read / 1.25x write. Latency did not move. Bedrock reports `inputTokens` **excluding** cached tokens, so any token or cost metric must add `cacheReadInputTokens` + `cacheWriteInputTokens` (`metrics.py` `prompt_total`) or the input count looks like it fell 99.98%.

## Optimization [verified 2026-11-06 on a live recommendation]
- `start_recommendation(type="SYSTEM_PROMPT_RECOMMENDATION", recommendationConfig={"systemPromptRecommendationConfig": {"systemPrompt": {"text": ...}, "agentTraces": {"cloudwatchLogs": {"logGroupArns": [runtime log group ARN], "serviceNames": ["<runtime name>.DEFAULT"], "startTime", "endTime"}}, "evaluationConfig": {"evaluators": [{"evaluatorArn": ...}]}}}, tags=...)` on the **data-plane** client (`bedrock-agentcore`). Exactly one evaluator; it must return a numerical value (single numerical scale for a custom LLM judge; no ground-truth placeholders, no multi-dimension). Prompt text up to 20,000 chars; name `[a-zA-Z][a-zA-Z0-9_-]{0,47}`. Status enum PENDING, IN_PROGRESS, COMPLETED, FAILED, DELETING; 167 sessions took ~12 minutes. `list_recommendations` returns `recommendationSummaries`. Result in `recommendationResult.systemPromptRecommendationResult.{recommendedSystemPrompt, explanation, configurationBundle, errorCode, errorMessage}`. `evals/recommend.py start|get|list`.
- **Diff every recommendation before using it.** The first one (`evals/recommendations/surv-prompt-rec-v1-*.diff`) inserted "Before proposing any disposition ... wait for explicit user approval. Do not treat silence as consent." (never in our prompt; would stop an unattended run before `propose_disposition`) while its explanation said it had *preserved* that invariant, and it optimised toward the judge's view (escalate market makers with a positive round trip), which is the opposite of the firm's metric. The optimizer sees the evaluator's score, not the gate or the safe close rate.
- Configuration bundles: `create_configuration_bundle(bundleName, components={<runtime ARN>: {"configuration": {...}}}, tags=...)` on the **control-plane** client returns `bundleId`, `bundleArn`, `versionId`. The Runtime app resolves a bundle from the request's W3C `baggage` header (`aws.agentcore.configbundle_arn=<arn>,aws.agentcore.configbundle_version=<id>`) through `GetConfigurationBundleVersion`, so the Runtime role needs `bedrock-agentcore:GetConfigurationBundle(Version)` (added in `agentcore/cdk/lib/cdk-stack.ts`; the CLI's role lacks it). `BedrockAgentCoreContext.get_config_bundle()` returns `{}` without a bundle and raises if the fetch fails; always fall back to code defaults. Our agent reads `system_prompt`, `model_id`, `effort` (`investigator.bundle_config`) and reports the bundle in `surv.bundle` and in the result; the harness sends the header with `--bundle name|<id>:<version>` (`evals/bundles.py`). An A/B test through the Gateway needs a Gateway *runtime* target (`httpRuntime`), an online evaluation config and SDK >= 1.8; multi-dimension evaluators are rejected.

## AgentCore CLI [verified 2026-11-02, CLI 1.0.1 installed, devguide pages cited]

- Package is `@aws/agentcore` (not `agentcore-cli`): `npm install -g @aws/agentcore`. Node 20.12+. Conflicts with the Python starter toolkit's `agentcore` command; don't install both.
- `agentcore add` resource types: harness, runtime, runtime-endpoint, gateway, gateway-target, gateway-connector, policy-engine, policy, credentials, memory, evaluator, online-eval, config-bundle, payment-manager. Everything is recorded in `agentcore/agentcore.json`; `agentcore deploy` creates it.
- The CLI deploys through AWS CDK (TypeScript) with `@aws/agentcore-cdk`; the generated stack is `agentcore/cdk/lib/cdk-stack.ts` and the `AgentCoreApplication` construct exposes `runtime(name)` / `harness(name)` as `IGrantable` ("Customize the CDK code"). ## Learned in the 2026-11-16 review (record integrity and IAM)
- **DynamoDB fine-grained access** [verified 2026-11-16, DynamoDB developer guide, "Using IAM policy conditions for fine-grained access control"]: with `ForAllValues:StringEquals` on `dynamodb:Attributes`, an attribute counts as accessed when the request names it anywhere, **including a ConditionExpression** (allowed attributes "can be read, written, or evaluated in a conditional write"; a role limited to them "cannot perform conditional write operations based on any other attributes"). So a write-limited role cannot condition on an attribute it is not allowed to write: the tools Lambda's proposal is conditioned on `decision_lock`, which is in its list, not on `recorded_disposition`, which is not. The key attributes of the table and of its indexes must be in the list. Grant `UpdateItem` only: `PutItem`, `DeleteItem` and `BatchWriteItem` replace or remove whole items. Restrict `dynamodb:ReturnValues` to NONE/UPDATED_OLD/UPDATED_NEW. A `ForAllValues` condition is true when the key is absent. moto does not evaluate any of this: `src/tools/tests/test_gateway_tools.py` reads the attribute names out of the real update calls and compares them with `src/tools/case_fields.py`. Exercised live 2026-11-16 after `cdk deploy SurvFirm`: `propose_disposition` and `draft_stor_narrative` both write under the statement, and the write conditioned on `decision_lock` works (`scripts/policy_demo.py --user L2 --stor`).

## The Gateway throttle, traced [2026-11-18, from the Runtime's log and by probe]
- **Count the throttle from the Runtime's log, never from a run's results.** The agent retries a 429 inside its MCP client and the harness retries a failed invocation once, so both hide it. Run v6 showed 2 failed investigations; 78 of its 169 invocations had met a 429 and the agent had given up 11 times. `scripts/gateway_throttling.py <run folder>` reads the log and reports it. The Gateway's vended log has no record of a request it rate-limited (searched for 429, rate limit and throttle in the window: nothing).
- **Which limit answers is read from the position of the throttled request.** The log names neither the tool nor the limit. A ten-tool investigation makes 12 Gateway requests (three to open the MCP session, nine tools within a few seconds), the model writes the report for 10 to 15 s, and request 13 is `propose_disposition`. In run v6 all 78 throttled requests were request 13, 9 to 16 s after the previous one: the write limit (`per-analyst-writes`, 3 a minute per analyst and tool), not the request limit (60 a minute), which was not seen to answer once. The first diagnosis blamed the request limit, and it was raised to 120 for an hour on that; it is back at 60.
- **A rate limit is counted before the policy.** A proposal that the policy would deny still uses up the write limit: 50 denied proposals in 9 s as one analyst got 25 answers of 429. And the limit is per analyst: at the same moment 12 proposals as a second analyst got none. So the write limit can be probed with proposals that write nothing, and saturating one analyst's limit does not touch another's.
- **The limiter is not a strict bucket.** Refusals and admissions alternate under load (the 50-call probe: `X..X.XX......X.......XXXXXX.X.X...`), and a request that waits can lose to fresh ones. With one analyst for two parallel investigations the demand is nearly four proposals a minute against three: with the agent waiting 2, 4, 8, 16 and 32 s (Runtime v20) the give-ups fell from 11 to 4 in a full run and did not reach zero. Waiting turns a short excess into a delay; it cannot serve a demand that stays above the limit.
- **So an evaluation run gives each worker its own analyst** (`l1.analyst`, `l1.analyst2`; `evals/run_dataset.py` takes every `SURV_L1*_USER` in the credentials file, round-robin by worker thread). Two workers under one analyst is one person doing two people's work, which is what the limit is there to slow down. Do not raise a limit to quiet a test harness; find out who is being limited first. Verified on slice `20261118T1343-two-analysts-slice`: no 429 in 30 invocations (0 of 14 and 0 of 15 per analyst), against 75 of 167 in the full run made the same day with one analyst. One analyst at one investigation at a time was never throttled either (0 of 72, `20261117T1454-seed9-variance`).
- **The limiter remembers a burst for minutes.** A first two-analyst slice, started three minutes after the probe above, was throttled for both analysts (12 of 30 invocations, one wait of 62 s) and had to be discarded; the repeat 25 minutes later was clean. A probe that saturates a limit and a measurement do not share an analyst and an hour.
- **`agentcore.json` endpoint descriptions are limited to 200 characters**: a longer one fails the deploy before anything is changed (`Too big: expected string to have <=200 characters at runtimes[0].endpoints.demo.description`). `test_the_project_file_fits_the_cli_limits` checks it.
- **A promotion check can fail on noise** [2026-11-18, corrected 2026-11-19]. Two full runs of one agent version (v7, v8 on Runtime v20) gave PASS and then FAIL, on "no false-positive scenario regressed to 0% close": F-STOP-1 went from 2 of 6 closed to 0 of 6. George decided to correct the check and accepted the floor that was recommended to him (the two numbers are our recommendation, not his judgement): the fall counts only when the previous run closed at least 3 alerts and at least four in five of the scenario (`ZERO_FLOOR_N = 3`, `ZERO_FLOOR_RATE = 0.8` in `evals/metrics.py`; 2 and a quarter before). A scenario below the floor is named in the verdict ("below the floor, read the variance run") and read on the variance run, so a change to the prompt or the standards needs one: 26 alerts x 5, about $10 and 35 minutes, the alert list and the baseline in `evals/runs/20261119T0023-variance-v20-26`. `run_dataset.py --rescore <run>` recomputes a run's verdict from its saved responses and keeps the judges' and the faithfulness results; saved runs otherwise keep the verdict they were given. Any further change to the rule is George's decision: ask first.
